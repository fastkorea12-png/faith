## P0 — 반드시 플레이테스트 전에 고칠 것

### P0-1. 03 장부: 웹이 정답 매핑을 미리 보여줘서 핵심 추리가 통째로 사라진다

- **근거**: `game.js:302-303`
  ```js
  if (state.step === "search") flow.innerHTML = `...${items.map(x => `<button data-found="${x.id}" ...>${x.mark} ${x.item}<small>${x.found}</small></button>`)...}`;
  if (state.step === "restore") flow.innerHTml... `<div class="shelf-stack">${[1,2,3,4,5,6].map(n => `<div><b>선반 ${n}</b><span>${items.find(x => x.shelf === n).mark} ${items.find(x => x.shelf === n).item}</span></div>`)...}`;
  ```
  대조: `stage-03.md:79-90` (5.2절)은 웹이 **"물은 가장 아래 선반에 둔다" 같은 관계 문장 6개만** 보여주고, 참가자가 그 문장을 근거로 물리 매트에 카드를 직접 배치해야 한다고 명시한다("참가자는 숫자를 계산하지 않고 카드 위치를 복원한다").

- **실제로 벌어지는 일**:
  1. `search` 단계에서 각 카드 버튼에 `x.found`(실제 발견 위치: 밀=조리대, 기름=출입구, 소금=조리대 등)가 **참가자가 현장에 나가기도 전에** 화면에 그대로 찍혀 있다. 수색 담당 A/B가 구역을 나눠 "발견 위치를 기록"하는 협동 작업(패킷 §3, §4)이 무의미해진다.
  2. `restore` 단계에서는 한 술 더 떠서, 선반 1~6에 어떤 품목이 와야 하는지 **정답 매핑 전체(건과일/밀/기름/소금/콩/물 = 1~6번)를 이미 계산된 상태로** 그대로 출력한다. 참가자가 "물은 가장 아래, 콩은 물 위…" 문장을 스스로 추론할 필요가 없다.
  3. 두 화면을 나란히 보면, "밀은 조리대에서 발견됐는데 원래는 선반 2"처럼 **위치 불일치가 자동으로 드러난다.** 즉 `audit`(변경 기록 감식)이나 `accuse`(범인 추리) 단계를 진행하기 전에 이미 "밀/기름/소금이 조작됐다"는 결론과 "4-3-2"라는 최종 번호까지 사실상 다 나와 있다.

- **참가자 혼란/체감**: 팀은 "먼저 처리" 문구를 비교하거나 권한표를 대조하는 추리를 할 필요 없이, 두 화면을 눈으로 훑고 버튼을 순서대로 누르기만 하면 끝난다. 12~18분 설계가 무색하게 5분 내외로 끝날 가능성이 높고, 정작 이 스테이지의 존재 이유인 "청지기" 메시지(맡은 것을 원래 뜻대로 복원·설명하는 경험)를 체험하지 못한 채 통과한다. 통과 기준 §13 "대학생 4~6명이 설명 없이 18분 안에 완료" 같은 지표는 통과하겠지만, 그건 게임이 쉬워서가 아니라 **정답이 노출돼서**다.

- **수정안**:
  - `search` 단계: 버튼 라벨에서 `x.found`를 빼고 품목명/표식만 노출한다. 발견 위치는 참가자가 직접 현장에서 확인하고 팀 포렌식 기록지(또는 별도 입력 UI)에 스스로 적게 한다.
  - `restore` 단계: 여섯 문장(`shelf-clues`)만 보여주고, `shelf-stack`은 **참가자가 직접 배치할 수 있는 빈 슬롯**(카드 선택 → 선반에 드래그/클릭 배정)으로 바꾸거나, 아예 이 단계의 검증을 웹에서 하지 않고 "물리 매트에 실제로 복원하십시오"라는 지시문 + 셀프 체크 버튼만 두는 패킷 원안대로 되돌린다. 정답 매핑을 계산해서 그대로 출력하는 로직 자체를 제거해야 한다.

### P1-3. 03 장부의 최소 인원(4~6명)이 다른 스테이지(3~6명)와 어긋나고, 3인 팀 대응 지침이 없다

### P2-1. 02 숙소: 이름표/약속카드 상태 도장 문구가 웹과 패킷 표기가 다르다

### P2-3. 02 숙소: 휴대폰 화면의 시계가 "11:13"으로 고정돼 있어 스테이지 00의 "H-11-13"(히브리서 11:13) 학습 효과와 은근히 충돌한다
